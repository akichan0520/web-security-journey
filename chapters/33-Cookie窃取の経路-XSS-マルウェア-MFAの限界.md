# 第33章：Cookie窃取の経路：XSS・マルウェア・MFAの限界

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
XSS、端末内の窃取、セッション固定、CSRFを分類でき、認証強化とセッション保護の違いを説明する。

## 全体像
攻撃の成立経路は1つではない。JS APIからの読み取り、マルウェアによる端末内窃取、XSSでの不正操作、セッション固定などは原因と防御が異なる。

## 🎙 読み上げ可能な講師ナレーション
最近のセッション乗っ取りを考える際、XSSと情報窃取型マルウェアを区別しましょう。HttpOnlyが付いていても、感染端末から情報が漏れる場合があります。反対にHttpOnlyによってCookie文字列が読めなくても、XSSでログイン中の画面に不正操作をさせる危険は残ります。二段階認証はログインを強くしますが、発行後のセッションを盗ませない対策も必要です。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```javascript
// 反例：入力をHTMLとみなして差し込む
welcome.innerHTML = userDisplayName;
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```javascript
// 改善：ユーザー入力を普通の文字列として表示する
welcome.textContent = userDisplayName;
// Cookieを守るHttpOnlyも併用するが、それだけでXSSは解決しない。
```

## 3. 一行ずつ意味を説明する
1. innerHTMLは入力内容をHTMLとして解釈し得る。
2. textContentは入力を文字列としてDOMへ挿入する。
3. HttpOnlyはCookieのJS APIからの閲覧を抑制する。
4. 端末内マルウェアはCookie属性で除去できない。
5. MFAは認証時の防御であり、盗難セッションの再利用とは対策が異なる。

## 4. 頭の中で処理の流れを追う
①外部データが画面へ→②HTMLとして解釈されるとXSS危険→③安全なDOM APIに修正→④端末感染によるCookie窃取は別の防御領域

### 根本原因
未信頼データがブラウザでコードとして処理される可能性がある。さらに端末内窃取はXSSとは別の入口なので両方の対策が必要。

### 修正の原理
XSS対策・端末防御・セッション管理は対象となる原因が異なる。防御を多層化する必要がある。

### 防御を重ねるとしたら
安全なDOM APIと文脈別エスケープ、HttpOnly、端末防御、失効・リスクに応じた再認証を組み合わせる。

## 5. 紙上ハンズオン（実行不要）
HttpOnly Cookieを使っていても不正な画面操作は発生し得る？ XSSとCookie窃取を区別して説明しよう。

**確認課題：**
攻撃用コードを試さず、改善例が防ぐ範囲・防がない範囲をそれぞれ1つ以上説明する。
