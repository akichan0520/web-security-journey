# 第15章：PDOとプレースホルダー・SQLインジェクション対策

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 中級

## この章でできるようになる
SQL文字列連結が危険な理由と、PDO::prepareとexecuteの役割を説明する。

## 全体像
SQL構文とユーザーの値を分離する。値にSQLらしい文字が含まれても「データ」として扱う。

## 🎙 読み上げ可能な講師ナレーション
SQLインジェクションは、入力した文字列が単なる値ではなくSQL構文として解釈されることから始まります。正しい基本はプレースホルダーです。特殊文字を無理に消すのではなく、SQLの形を固定して値だけを渡します。さらに権限を必要最小限にします。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
// 脆弱：SQLの構文へ利用者の値を連結
$keyword = $_GET['q'] ?? '';
$sql = "SELECT id, title FROM catalog WHERE title = '$keyword'";
$rows = $pdo->query($sql)->fetchAll();
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
// 安全：SQL文の形を固定し、値は別に渡す
$keyword = (string) ($_GET['q'] ?? '');
$stmt = $pdo->prepare('SELECT id, title FROM catalog WHERE title = :q');
$stmt->execute([':q' => $keyword]);
$rows = $stmt->fetchAll(PDO::FETCH_ASSOC);
```

## 3. 一行ずつ意味を説明する
1. $keywordはブラウザからの入力であり、信頼できない。
2. 危険版はSQL本文に$keywordを連結するため、命令とデータが混ざる。
3. prepareでSQLの形を固定し、executeで値を別に渡す。
4. 値用のプレースホルダーをテーブル名や列名には直接使えないため、識別子は許可リストで選ぶ。

## 4. 頭の中で処理の流れを追う
① 入力にシングルクォートが含まれる想定→② 危険版はSQL文字列の境界が崩れる可能性→③ 安全版は値として束縛→④ SQL構造は変わらない。

### 根本原因
未信頼データがSQL文そのものに入り、WHERE条件を書き換えられる。

### 修正の原理
危険なのは引用符だけではない。SQL構文を文字列連結で作ると未信頼値がSQLの意味を変えうる。prepare/executeは命令とデータを分ける。テーブル名など識別子は許可リストで限定。

### 防御を重ねるとしたら
$pdo->prepareとbind/execute。テーブル名等はプレースホルダー化できないので許可リスト化。
