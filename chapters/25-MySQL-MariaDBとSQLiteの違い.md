# 第25章：MySQL・MariaDBとSQLiteの違い

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** DB応用

## この章でできるようになる
SQL方言・クライアント/サーバー方式・InnoDB・インデックス・権限を比較する。

## 全体像
SQLiteはファイル内DB。MySQLは別のDBプロセスへ接続し、ユーザーとDB単位の権限を持つ。

## 🎙 読み上げ可能な講師ナレーション
ここからはデータベースを横断的に見ます。SQLiteは小さな教材に向きますが、MySQLやMariaDBは専用のDBサーバーを使います。アプリ用ユーザーには必要なテーブルへの権限だけ渡しましょう。インデックスやトランザクションを扱う際はストレージエンジンも意識します。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```sql
-- 危険な権限例（意図を読むだけ）
GRANT ALL PRIVILEGES ON *.* TO 'webapp'@'%';
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```sql
-- 概念例：専用DBの必要な操作だけを許可
GRANT SELECT, INSERT, UPDATE ON training.notes TO 'webapp'@'app-host';
-- DB方言・バージョン・権限モデルに応じて要調整
```

## 3. 一行ずつ意味を説明する
1. ALL PRIVILEGESはアプリ機能に比べて過大な権限になりやすい。
2. SELECT/INSERT/UPDATEは業務上必要な操作だけを表す。
3. 接続元の指定やGRANT文の詳細はDB製品や設定で差がある。

## 4. 頭の中で処理の流れを追う
① アプリが必要な操作を洗い出す→② 専用DBと専用アカウント→③ 必要な権限だけ。

### 根本原因
SQLインジェクションなどで侵害された場合の被害範囲が広がる。

### 修正の原理
SQLiteは埋め込みDB、MySQL系はDBサーバー。ユーザー認証・接続制御・権限設計は同じではない。最小権限を理解する。

### 防御を重ねるとしたら
アプリ専用DB/ユーザーと最小権限、値はプリペアドステートメントでバインド。
