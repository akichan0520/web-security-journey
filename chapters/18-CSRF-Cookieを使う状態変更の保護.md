# 第18章：CSRF：Cookieを使う状態変更の保護

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
CSRFの成立条件、CSRFトークン、SameSiteの違いを理解する。

## 全体像
攻撃側は利用者のCookieが付く要求を誘導できる場合がある。サーバーは意思確認のためトークンを検証する。

## 🎙 読み上げ可能な講師ナレーション
CSRFは、利用者がログインしているブラウザを使わせ、意図しない操作を送らせる問題です。今回はメモ追加・削除のリクエストにセッション固有のトークンを要求します。検証は必ずサーバー側で行いましょう。GETで状態を変更しない設計も大切です。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
// 危険：ログインCookieだけで更新を受け付ける
if (isset($_SESSION['user_id'])) updateProfile($_POST);
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
// 説明用の断片：状態変更時にサーバーで照合
$received = $_POST['csrf_token'] ?? '';
$expected = $_SESSION['csrf_token'] ?? '';
if (!is_string($received) || !is_string($expected)
    || $expected === '' || !hash_equals($expected, $received)) {
    http_response_code(403); exit;
}
updateProfile($validatedInput);
```

## 3. 一行ずつ意味を説明する
1. $_POSTのトークンはブラウザから受け取る値。
2. セッション側の期待値とhash_equalsで比較し、欠落・不一致を拒否。
3. トークン発行・HTMLへの安全な埋め込み・Cookie設定・SameSite等は別の設計要素。

## 4. 頭の中で処理の流れを追う
① 第三者ページからの要求を想定→② Cookieは自動で送られる可能性→③ トークンの欠落・不一致を403で拒否。

### 根本原因
別のページから意図しないリクエストを送られる可能性がある。

### 修正の原理
ブラウザはCookieを自動送信するため、ログイン状態だけではユーザーが意図した操作と区別できない。CSRFトークンはセッションと結び付け、サーバー側で照合する。

### 防御を重ねるとしたら
トークン、SameSite、Origin検証などを適切に組み合わせる。XSSにも別途対応。
