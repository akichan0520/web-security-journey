# 第17章：XSS：反射・格納・DOMの3種類

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
XSSの3つの典型形と表示コンテキスト、CSPの役割と限界を説明できる。

## 全体像
危険の本質は「未信頼の文字列をHTMLやスクリプトとして解釈させる」こと。

## 🎙 読み上げ可能な講師ナレーション
XSSには、リクエストをそのまま画面へ返す反射型、データベース等に保存した内容を後から表示する格納型、ブラウザのDOM操作で発生する型があります。まず文字列がどの場所に入るかを見てください。HTML本文、属性、URL、JavaScript文字列はそれぞれ安全な扱いが異なります。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
<?php
// 危険：外部値をHTML文脈へ直接出力
echo '<' . 'p>' . ($_GET['q'] ?? '') . '</p>';
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
<?php
$text = (string) ($_GET['q'] ?? '');
echo '<p>' . htmlspecialchars(
    $text, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'
) . '</p>';
// ブラウザDOMへ文字を置くなら textContent
```

## 3. 一行ずつ意味を説明する
1. 危険版のechoは外部値をHTML本文へ直接差し込む。
2. htmlspecialcharsはHTML本文の特別な文字をエンコードする。
3. JavaScriptのDOMではtextContentがテキスト表示の基本。文脈によって別の処理が必要。

## 4. 頭の中で処理の流れを追う
① 入力は文字列→② 危険版はHTMLとして解析→③ 安全版は&や<等を符号化→④ テキストとして表示。

### 根本原因
ブラウザのHTMLパーサが未信頼の文字列を要素や属性に変換する。

### 修正の原理
HTML本文へ未信頼入力をそのまま挿入するとタグとして解析されうる。HTML本文、属性、URL、JavaScript文字列では異なる規則が必要。ここではHTML本文を対象にする。

### 防御を重ねるとしたら
文脈ごとに適切なエンコード。HTML本文ではhtmlspecialchars。DOMテキストはtextContent。CSPは追加防御。

## 5. 紙上ハンズオン（実行不要）
質問：CSPを付ければHTMLエスケープは不要？ まず答えを見ずに、危険版のどの部分が原因となるか一行で説明してください。
