# 第05章：フォーム・GET/POST・入力検証

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 基礎

## この章でできるようになる
フォーム送信、name属性、入力制限、クライアント検証とサーバー検証の差を理解する。

## 全体像
ブラウザ側のrequiredやmaxlengthはユーザー体験向上。サーバーは必ず自分で検証する。

## 🎙 読み上げ可能な講師ナレーション
ブラウザの入力欄は便利ですが、開発者ツールやAPI直接送信でHTMLの制約を迂回できます。大切なのはサーバーが信頼境界です。表示するエラーメッセージも入力全体をそのまま埋め込まないようにします。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```html
<form method="post">
  <input name="age" type="number" min="0" max="120">
</form>
// PHPで$_POST["age"]をそのまま信用する
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```html
// 画面側チェックに加え、受信側で型と範囲を確認
$age = filter_input(INPUT_POST, 'age', FILTER_VALIDATE_INT);
if ($age === false || $age === null || $age < 0 || $age > 120) {
    http_response_code(422);
    exit('invalid age');
}
```

## 3. 一行ずつ意味を説明する
1. filter_input(..., FILTER_VALIDATE_INT)は整数としての妥当性を検証する。
2. false/nullを除外した上で範囲を確認する。
3. この例は入力条件を説明する断片で、実際の業務では認可やCSRFも必要。

## 4. 頭の中で処理の流れを追う
① HTMLの制限を読む→② 要求の値は信用しない→③ PHPで検証→④ 妥当な値だけ先へ渡す。

### 根本原因
攻撃者や別クライアントはフォームを経由する必要がないから。

### 修正の原理
入力フォームの属性は使いやすさを高めるが、HTTP要求はフォーム以外からも作れる。サーバーは入力の意味・範囲・型を確認する。

### 防御を重ねるとしたら
サーバーで型、サイズ、必須項目、権限を検証。HTMLの検証は補助。
