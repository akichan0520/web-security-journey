# 第20章：ファイルアップロード・パス操作・SSRF

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
アップロードやパス/URL入力が危険になる条件を把握し、安全な設計を提案できる。

## 全体像
ファイル名もURLも未信頼入力。サーバーがどこへ保存・接続するかが境界になる。

## 🎙 読み上げ可能な講師ナレーション
ファイルの拡張子だけで安全を判断できません。受け入れる形式、サイズ、内容、保存位置を限定します。また利用者指定のURLへサーバーがアクセスする機能はSSRFの原因になります。今回は実行可能な危険機能は作らず、設計レビューに集中します。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
// 危険：入力値からサーバーの保存パスや接続先を決める
$path = __DIR__ . '/uploads/' . $_FILES['image']['name'];
$url = $_POST['preview_url'];
// どちらも検証せずに後続処理へ渡す
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
// 設計上の修正（この断片だけで安全にはならない）
if ($_FILES['image']['size'] > 2_000_000) rejectUpload();
// 実体判定・形式変換・権限・保存先保護も必要
$storageName = bin2hex(random_bytes(16)) . '.png';
// 外部URL取得は宛先制限とDNS/IP再検査を設計する
```

## 3. 一行ずつ意味を説明する
1. 元のファイル名をそのまま保存パスに利用すると、パスが信頼できるか判断できない。
2. random_bytesで推測しにくい名前を生成するが、拡張子や内容の安全性は別問題。
3. SSRFは宛先制限・DNS再解決・リダイレクト・ネットワーク分離を含めて設計する。

## 4. 頭の中で処理の流れを追う
① 受け取ったファイル名・URLを未信頼として分類→② 期待する形式/サイズ/宛先を定義→③ サーバーで判定。

### 根本原因
../によるパストラバーサルや内部宛てリクエスト、危険な形式の配信を招く。

### 修正の原理
パス・ファイル名・URLは入力次第で想定外の保存先や接続先を指せる。拡張子だけの検査では不十分。SSRF対策はリダイレクトと名前解決の変化も考える。

### 防御を重ねるとしたら
許可リスト、内容検査、上限、公開ディレクトリ外保存、認可、接続先制限を設計する。
