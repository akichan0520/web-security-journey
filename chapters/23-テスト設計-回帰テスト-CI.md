# 第23章：テスト設計・回帰テスト・CI

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 応用

## この章でできるようになる
正常系と異常系、境界値、回帰テスト、GitHub Actionsの位置づけを理解する。

## 全体像
安全なコードは書いて終わりではなく、破られたはずの条件が毎回守られているかを自動確認する。

## 🎙 読み上げ可能な講師ナレーション
修正したつもりの問題が後の変更で戻ってくることを回帰と呼びます。今回は正常な検索のほか、SQLの入力が構造を変えないこと、IDORを拒否すること、CSRFを拒否することをテストにします。CIではPHP構文検査と、SQLite付き環境でHTTPテストを実行します。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```text
// 正常な入力1つだけテストする
assert(search('apple') !== null);
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```text
// 疑似テスト: 実行はせず、期待する仕様をレビュー
cases = [
  ('自分のメモ', '200'),
  ('他人のメモ', '404 or 403'),
  ('CSRFトークン欠落', '403'),
  ('SQLメタ文字入り検索', '命令構造は不変'),
]
for (scenario, expected) in cases:
  print(scenario, expected)
```

## 3. 一行ずつ意味を説明する
1. 正常系だけでなく、失敗すべきリクエストにも期待値を定義する。
2. 403/404のどちらを返すかは情報漏えい要件とAPI設計によって変わりうる。
3. ここでは擬似的な期待表の読解であり、テストコード実行は含まない。

## 4. 頭の中で処理の流れを追う
① 想定する仕様を列挙→② 失敗条件を先に書く→③ 期待する拒否コードと理由を言語化する。

### 根本原因
悪意ある入力や認可違反の再発を見逃す。

### 修正の原理
正常系だけでは境界条件の不備を見落とす。認証・認可・入力検証・表示の各信頼境界に負のテストを用意する。ここではテストケースの読み取りに留める。

### 防御を重ねるとしたら
認証なし、トークンなし、他ユーザーID、HTML文字列、SQL風文字列を回帰テストへ組み込む。
