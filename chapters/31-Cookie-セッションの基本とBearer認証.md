# 第31章：Cookie・セッションの基本とBearer認証

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
Cookieとログインを混同せず、Set-Cookie→Cookie→サーバー照合の順序を説明し、窃取時の危険を言語化できる。

## 全体像
Cookieはブラウザが自動送信する名前と値。IDの有効性と権限を判断するのはサーバーであり、すべてのCookieが認証情報ではない。

## 🎙 読み上げ可能な講師ナレーション
まず、ログイン画面とCookieを分けて考えましょう。利用者の本人確認が終わると、サーバーはランダムなセッション識別子を発行できます。次の要求では、ブラウザが対応するCookieを送信し、サーバーが認証済みの状態を引き当てます。誰かが有効な識別子を知れば、パスワードを使わずにその状態を再利用できる実装があります。これがBearer方式のリスクです。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
// 反例：Cookieに値があるだけでログイン済みとみなす
if (isset($_COOKIE['session'])) {
    $loggedIn = true;
}
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
// 改善の設計モデル（処理の責務だけを示す疑似PHP）
$sid = $_COOKIE['__Host-session'] ?? null;
$record = validateSessionServerSide($sid); // 保存先で照合
if ($record && !$record->revoked && !$record->expired) {
    $userId = $record->userId;
    // 各処理で対象データに対する認可も行う
}
```

## 3. 一行ずつ意味を説明する
1. $_COOKIEはブラウザから送られた値であり、サーバーが信用してよいとは限らない。
2. セッション保存先で有効なIDと一致するかを確認する。
3. 失効と時間制限はブラウザ任せではなくサーバーで評価する。
4. ログイン済みであることと操作対象への権限は別物。

## 4. 頭の中で処理の流れを追う
①認証成功→②サーバーがID発行→③Set-Cookieでブラウザへ→④次回Cookieを送る→⑤サーバーが失効・期限・ユーザーを検証→⑥認可して応答

### 根本原因
Cookie値は利用者が編集できる。存在だけでは正当なセッションか判断できず、偽装や不正な利用を受け入れ得る。

### 修正の原理
認証済みセッションの秘密は、有効な時のみ本人の継続性を示す。Cookieの存在だけを信用しない。

### 防御を重ねるとしたら
サーバーの保存先でIDの存在、失効、期限、ユーザー状態を検証し、操作ごとに認可する。

## 5. 紙上ハンズオン（実行不要）
Cookieの値だけは存在するが、保存先に対応するセッションがない場合、ログイン済みと判定してよいだろうか？
