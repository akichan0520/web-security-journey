# 第29章：REST API設計・CORS・制限と本番化の判断

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 応用

## この章でできるようになる
API設計とメソッド・ステータス、CORS、レート制限、運用段階で追加する対策を説明する。

## 全体像
CORSはブラウザから別オリジンの応答を読めるかを制御するもの。認証・認可の代わりではない。

## 🎙 読み上げ可能な講師ナレーション
APIは端末、ブラウザ、外部クライアントから利用されます。CORSを設定しただけでは不正アクセスを止められません。実際に外部公開するにはHTTPS、認証試行回数制限、権限設計、監視、依存更新、秘密管理などが必要です。今回のPHPアプリは、あくまでローカルで仕組みを学ぶ教材です。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```text
// 危険な思い込み
header('Access-Control-Allow-Origin: *');
// これで認証と認可が完了、と考える
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```text
// CORSは別オリジンへのブラウザ応答読取制御
$allowedOrigins = ['https://app.example.invalid'];
if (in_array($origin, $allowedOrigins, true)) {
    header('Access-Control-Allow-Origin: ' . $origin);
    header('Vary: Origin');
}
// 認証・認可・CSRF等は別途必要
```

## 3. 一行ずつ意味を説明する
1. Access-Control-Allow-Originは別オリジンからのブラウザ読取に関係する。
2. 許可するOriginは厳密に比較し、Vary: Originでキャッシュの整合性を考慮する。
3. CORSは認証や認可を代行しない。資格情報付き要求はさらに別途慎重な設計が必要。

## 4. 頭の中で処理の流れを追う
① Originを認識→② 許可するオリジンを照合→③ CORS応答→④ API内で別途認証・認可。

### 根本原因
CORSは応答共有の仕組みであって、バックエンドの権限判断を保証しない。

### 修正の原理
CORSはブラウザ側のクロスオリジン読み取りポリシーで、APIのログイン認証ではない。サーバー間要求や直接アクセスを防ぐ仕組みでもない。

### 防御を重ねるとしたら
認証・認可・最小権限・通信保護・濫用制限・運用監視を多層化する。
