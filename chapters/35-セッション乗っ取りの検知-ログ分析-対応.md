# 第35章：セッション乗っ取りの検知・ログ分析・対応

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
IP/UA変化の偽陽性・偽陰性を理解し、資格情報をログに残さない監視・失効・再認証の流れを設計する。

## 全体像
検知はIPだけでは確定しない。アクセス傾向、端末特性、重要操作を複合評価し、必要な時にサーバー側でセッションを制限する。

## 🎙 読み上げ可能な講師ナレーション
ログ分析では、同じセッションに普段と大きく異なる端末特性や操作が出ていないか調べます。ただし移動やVPNだけでもIPが変化し、偽陽性が生じます。逆に同じIPでも侵害の可能性は消えません。原則としてセッションIDの生値をログへ書かず、必要なら疑似化した相関IDを用います。異常時は高リスク操作を止め、適切な再認証とサーバー側失効へ進みます。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
// 反例：セッション秘密を丸ごとログに記録
error_log($_SERVER['HTTP_COOKIE'] ?? '');
// かつ、IPが変化したら即「侵害確定」と判断
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
// 改善：危険な識別子を生ログに残さない（説明用）
$auditEvent = [
  'event' => 'session_risk_review',
  'session_alias' => $nonReversibleCorrelationId,
  'risk_signals' => ['device_change', 'sensitive_action'],
  'decision' => 'reauthentication_required',
];
// 相関IDの作り方・保存ポリシー・失効処理は別途設計
```

## 3. 一行ずつ意味を説明する
1. Cookieヘッダーには認証用IDが含まれる場合があり、通常ログに残してはならない。
2. セッションの追跡には生のIDではなく安全な相関IDを検討する。
3. 端末変化や操作リスクなど複数のシグナルを用いて総合的に評価する。
4. 再認証が必要なら古いセッションをサーバー側で制限・失効する。
5. 監視は誤検知と見逃しがあるため、プライバシーと利用者負担に配慮する。

## 4. 頭の中で処理の流れを追う
①疑似化セッションIDを監査→②新規の端末・操作の変化→③リスク評価→④重要操作を制限→⑤セッション失効と再認証→⑥事後分析

### 根本原因
生のCookieがログから漏えいすると二次侵害になり得る。またモバイル回線切替やVPNでIPは変化し誤検知が多い。

### 修正の原理
セッション検知は確率的な評価であり、生Cookieの漏えいを起こさず、被害を限定する運用が必要。

### 防御を重ねるとしたら
疑似化したセッション相関ID、権限変更や操作種別、リスク信号の多角的評価、再認証と失効、保管制限を組み合わせる。
