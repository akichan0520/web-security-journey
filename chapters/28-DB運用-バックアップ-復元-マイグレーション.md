# 第28章：DB運用：バックアップ・復元・マイグレーション

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** DB応用

## この章でできるようになる
バックアップ、復元試験、スキーマ変更、秘密情報とテストデータの分離を設計できる。

## 全体像
バックアップは取得するだけでなく復元できることを定期確認して初めて意味を持つ。

## 🎙 読み上げ可能な講師ナレーション
アプリが長く運用されるとテーブル構造が変わります。場当たり的に本番DBだけ修正すると再現性がなくなります。マイグレーションは変更をバージョン管理し、テスト環境で適用してから本番へ進めます。バックアップでは個人情報の保護も重要です。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```text
# 危険：本番データやDBダンプをリポジトリへ置く
repo/production-users-dump.sql
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```text
# GitHubに掲載するのは空のスキーマと架空サンプル
schema.sql     # CREATE TABLE ...
examples.md    # ダミーデータのみ
# 本番バックアップはアクセス制御・暗号化・復元試験を別に管理
```

## 3. 一行ずつ意味を説明する
1. バックアップは秘密情報を大量に含むことがある。
2. スキーマ公開とデータ公開は別問題。練習用の架空サンプルと分ける。
3. 復元の確認ができないバックアップは事業継続の保証にならない。

## 4. 頭の中で処理の流れを追う
① バックアップ取得の目的→② 秘密を含むか→③ 保存先・暗号化→④ 復元して整合性を検証。

### 根本原因
個人情報・認証情報・機密データを公開してしまう。

### 修正の原理
バックアップは存在するだけでは不十分。復元可能性・整合性・保管先の安全性・保持期間を設計する。公開リポジトリに実データを置かない。

### 防御を重ねるとしたら
ダミーデータだけ使う。DB本体・.envは.gitignore。暗号化・権限・世代管理・復元試験。
