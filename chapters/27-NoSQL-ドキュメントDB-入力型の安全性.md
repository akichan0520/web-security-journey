# 第27章：NoSQL・ドキュメントDB・入力型の安全性

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** DB応用

## この章でできるようになる
RDBとドキュメント型DBの特徴・トレードオフ、NoSQLインジェクションを概念として理解する。

## 全体像
NoSQLは安全性の保証名ではない。入力オブジェクトの型や演算子がクエリとして扱われる場合がある。

## 🎙 読み上げ可能な講師ナレーション
NoSQLは「SQLを使わないから安全」ではありません。JSONのオブジェクトをそのままDBの検索条件へ渡すと、利用者が演算子を含む条件を作れてしまう場合があります。どのデータをキーとして受け取るか、型を検証するのが基本です。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```javascript
// 疑似コード：ユーザーJSONをそのまま検索条件に渡す
const filter = JSON.parse(req.body.filter);
collection.findOne(filter);
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```javascript
// 疑似コード：許可した属性だけから条件を組み立てる
if (typeof req.body.username !== 'string') reject();
const filter = { username: req.body.username };
collection.findOne(filter);
```

## 3. 一行ずつ意味を説明する
1. JSON.parseした値がオブジェクトだと、利用者が条件の構造を操作できる場合がある。
2. typeofで型を限定してから、条件オブジェクトをサーバー側で構築。
3. 許可リストによる入力型と検索キーの制限が重要。

## 4. 頭の中で処理の流れを追う
① JSON入力を型で検査→② 操作子を含む構造を受け取らない→③ 許可したキーだけから検索条件を作る。

### 根本原因
クエリ演算子や型を攻撃者が指定でき、想定外の検索条件になることがある。

### 修正の原理
ドキュメントDBでは値の型が重要。利用者指定のオブジェクトをクエリ構造として受け入れず、サーバーが条件オブジェクトを構築する。

### 防御を重ねるとしたら
スキーマ検証、許可するキー/演算子の固定、最小権限、ライブラリの安全機能を利用する。
