# 第22章：エラーハンドリング・ログ・監視

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 応用

## この章でできるようになる
エラー処理、HTTPステータス、ログの守り方、監査ログと個人情報の境界を理解する。

## 全体像
利用者へは最小限のエラー、運用者へは調査に必要な記録。ただし秘密はログに残さない。

## 🎙 読み上げ可能な講師ナレーション
本番環境でSQLの内部エラーや接続情報が画面に出ると情報漏えいにつながります。利用者向けには一般的なエラーを返し、内部のログに調査の手掛かりを記録します。今回のaudit_logはメモの追加や削除を記録しますが、パスワードやセッショントークンは記録しません。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
catch (Throwable $e) {
    echo $e->getMessage();
    error_log('cookie=' . ($_SERVER['HTTP_COOKIE'] ?? ''));
}
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
try {
    handleRequest();
} catch (Throwable $e) {
    error_log('request failed: id=' . $requestId);
    http_response_code(500);
    echo 'エラーが発生しました';
}
```

## 3. 一行ずつ意味を説明する
1. 例外メッセージには内部パスやSQLや秘密値が含まれる場合がある。
2. ログには相関用のrequestIdなど必要最小限を入れる。
3. 利用者には一般的なエラーを返し、詳細な調査情報はアクセス制限された場所で管理。

## 4. 頭の中で処理の流れを追う
① 例外発生→② 監査に必要な非機密情報を記録→③ 利用者には詳細を出さず状態コードを返す。

### 根本原因
ログ保存先の漏えいで別の被害が発生する。

### 修正の原理
内部エラーやCookie/トークンは機密情報を含む。利用者向けエラーは最小限とし、ログも識別子・機密情報をマスキングして扱う。

### 防御を重ねるとしたら
ログは必要最小限、構造化、アクセス制御、保持期間設計。利用者への応答は一般化。
