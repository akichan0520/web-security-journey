# 第19章：IDOR・水平権限昇格・認可

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
IDORの原因と認証/認可の違い、オブジェクト単位の権限検証を説明できる。

## 全体像
URLのidを変えられることは普通。問題はサーバー側が所有者を見ずに他人の情報を返すこと。

## 🎙 読み上げ可能な講師ナレーション
IDORはログイン機能があるだけでは防げません。自分のメモIDを他人のIDに置き換えても、サーバーが所有者チェックをしていれば拒否できます。大切なのは「IDが推測しにくいか」ではなく、「この利用者がその対象を操作してよいか」です。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
// 危険：メモIDだけで取得
$stmt = $pdo->prepare('SELECT * FROM notes WHERE id = :id');
$stmt->execute([':id' => $requestedId]);
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
// 安全：セッション由来の利用者IDで範囲を限定
$stmt = $pdo->prepare(
    'SELECT * FROM notes WHERE id = :id AND owner_id = :owner'
);
$stmt->execute([':id' => $requestedId, ':owner' => $sessionUserId]);
```

## 3. 一行ずつ意味を説明する
1. 危険版は要求されたidだけで検索し、所有者を確認していない。
2. 安全版はid AND owner_idの両方を検索条件にする。
3. owner_idはユーザーが渡す値ではなく、認証済みセッションから導く。

## 4. 頭の中で処理の流れを追う
① AliceがBobのメモIDを指定した想定→② 危険版はIDだけで検索→③ 安全版はowner_idが不一致→④ 行を返さない。

### 根本原因
所有者や共有権限を確認していないため、他人のオブジェクトを取得できる。

### 修正の原理
IDを変えられること自体ではなく、対象IDの所有権を確認しないことが問題。所有者以外に共有を許可するなら、別の明示的な認可規則が必要。

### 防御を重ねるとしたら
WHERE id=? AND owner_id=? とし、全API操作で一貫して権限を検証する。

## 5. 紙上ハンズオン（実行不要）
質問：IDをUUIDにすれば所有者チェックは不要？ まず答えを見ずに、危険版のどの部分が原因となるか一行で説明してください。

**確認課題：**
安全側のコードを読んで、上の問題をどう防ぐか説明する。実行・HTTP要求・入力操作は不要。
