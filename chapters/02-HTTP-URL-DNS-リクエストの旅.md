# 第02章：HTTP・URL・DNS・リクエストの旅

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 入門

## この章でできるようになる
URLとHTTPの違い、DNS/TCP/TLS、メソッド、ステータス、ヘッダーと本文を区別する。

## 全体像
ブラウザ→DNS（名前解決）→接続→HTTP要求→Webサーバー→処理→HTTP応答→描画。

## 🎙 読み上げ可能な講師ナレーション
ブラウザが画面を出すまでに通信が起きます。URLのホスト名を解決し、サーバーに要求します。HTTPは何が欲しいかを伝えるルールです。GETは取得、POSTは作成などに使います。ただし、HTTPメソッド名だけでアクセス権限が保証されるわけではありません。開発者ツールのNetworkタブで本物のリクエストを読みましょう。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```text
GET /delete?id=3 HTTP/1.1
Host: example.invalid
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```text
GET /notes?id=3 HTTP/1.1
Host: example.invalid

# 状態を変更するならPOST/DELETE等を設計し、
# 認証・認可・CSRF対策も検討する。
```

## 3. 一行ずつ意味を説明する
1. GETはリソース取得を意図する。ブラウザやクローラーによるアクセスで副作用を起こさない設計が望ましい。
2. DELETEやPOSTもメソッドだけでは十分でない。主体の認証・対象の認可・CSRF設計が別に必要。

## 4. 頭の中で処理の流れを追う
① ブラウザがURLを解釈→② DNSで宛先解決→③ HTTPS/TLS→④ HTTP要求→⑤ サーバー応答。

### 根本原因
GETは取得用と期待され、リンク先の先読みやクローラーが実行する可能性がある。

### 修正の原理
GETは取得を意図するメソッド。リクエスト行、Host、ヘッダー、ボディの役割を区別する。GETを安全メソッドとして設計しないとリンク訪問だけで状態が変わりうる。

### 防御を重ねるとしたら
状態変更はPOST/PUT/DELETE等で行い、認証・認可・CSRF対策を別途行う。
