# 第32章：Cookie属性と安全なSet-Cookie設計

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
HttpOnly、Secure、SameSite、Domain、Path、__Host-、Partitionedの目的と限界を理解する。

## 全体像
Set-Cookieの属性はブラウザでのCookieの扱いを制御する。端末侵害や盗難後の単純再利用を属性だけで防ぐものではない。

## 🎙 読み上げ可能な講師ナレーション
HttpOnlyはJavaScriptからの読み取りを制限します。Secureは平文HTTPでの送信を制限し、SameSiteは別サイトからの要求に伴うCookie添付を制御します。三つとも役割は異なります。__Host-は適用先ホストを狭めるための接頭辞です。属性を一つ付ければ安全、とは考えず、何を防ぎ何を防がないかセットで理解しましょう。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```text
HTTP/1.1 200 OK
Set-Cookie: session=[架空ID]; Domain=example.test; Path=/; Max-Age=2592000
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```text
HTTP/1.1 200 OK
Set-Cookie: __Host-session=[架空ID]; Path=/; Secure; HttpOnly; SameSite=Lax
```

## 3. 一行ずつ意味を説明する
1. __Host-接頭辞は対応ブラウザで Secure・Path=/・Domainを付けない条件を強制する。
2. SecureはHTTPSで送信するための指定で、端末内のCookie情報の漏えいを防がない。
3. HttpOnlyは document.cookie での取得を制限するがXSSによる画面内操作は防がない。
4. SameSite=Laxは一部のクロスサイト要求へのCookie添付を制限するが、盗まれた値の直接利用は防がない。
5. 有効期限はサーバーでも管理し、盗難時に失効できるようにする。

## 4. 頭の中で処理の流れを追う
①サーバーからSet-Cookie→②ブラウザが属性を検証・保存→③条件に一致した要求にCookie送信→④サーバー側でセッション照合

### 根本原因
Cookieへのアクセス範囲が必要以上に広がり、ブラウザ内のスクリプトやHTTP送信による露出の余地が増える。

### 修正の原理
安全な属性は取得経路や送信条件を狭めるが、既に盗まれた有効セッションIDの失効ではない。

### 防御を重ねるとしたら
Cookie属性と__Host-の制約を適用し、サーバー側の失効・有効期間・XSS/CSRF対策も実施する。
