# 第34章：PHPで考えるセッション固定・再生成・期限・失効

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** セキュリティ

## この章でできるようになる
認証前後のID再生成、厳格モード、期限とログアウト時の失効の役割を説明できる。

## 全体像
セッション固定対策は、認証前に使っていたIDが認証後も有効な資格情報にならないようにすること。失効と期限はサーバー側で管理。

## 🎙 読み上げ可能な講師ナレーション
セッションIDの問題は盗難だけではありません。ログイン前から使われていたIDをログイン後にも継続すると、セッション固定の危険があります。PHPでは strict mode を有効にして未発行IDの採用を抑え、認証成功などの権限変化でIDを再生成します。ただし再生成も競合や一時的な不安定さに配慮する必要があります。さらにCookie削除だけでなくサーバー側で失効させることが必要です。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```php
// 反例：ログイン前のIDを引き継ぐ
session_start();
if ($verified) {
    $_SESSION['user_id'] = $userId; // 同じIDのまま認証済み
}
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```php
// 設計要点のみを示すPHP抜粋
ini_set('session.use_strict_mode', '1');
session_name('__Host-session');
session_set_cookie_params([
  'path' => '/', 'secure' => true,
  'httponly' => true, 'samesite' => 'Lax',
]);
session_start();
if ($verified) {
    session_regenerate_id(false); // 旧IDの扱いは期限で別途制御
    $_SESSION['user_id'] = $userId;
}
// 旧IDの失効・期限・競合対策は別途必須
```

## 3. 一行ずつ意味を説明する
1. use_strict_mode=1で未発行IDの受け入れを抑える（ハンドラーのサポートが必要）。
2. __Host-sessionを使用するとブラウザ側にもCookie属性の整合性を要求できる。
3. 権限変化時にセッションIDを切り替えて固定攻撃リスクを減らす。
4. false指定は旧IDデータをただちに削除しないため、旧IDの期限・失効は設計で補う。
5. サーバー側の失効、アイドル期限、絶対期限は省略できない。

## 4. 頭の中で処理の流れを追う
①匿名セッション→②本人確認成功→③別の識別子を発行→④認証済み情報を新しいIDへ→⑤旧IDの失効・期限を判断→⑥各要求で認可

### 根本原因
ログイン前のIDに認証済み権限が紐づく可能性があり、過去に複製されたIDもサーバー側で有効なままになり得る。

### 修正の原理
認証成功時の識別子の切替と、サーバー側でのセッション失効・期限が重要。コードは全処理の一部分。

### 防御を重ねるとしたら
strict mode、権限変化時の再生成、サーバー側の期限・失効、並列リクエストを考慮した再生成を設計する。
