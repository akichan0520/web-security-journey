# 第12章：RDBとSQLite：主キー・外部キー・制約

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 中級

## この章でできるようになる
テーブル/行/列、主キー、外部キー、NULL、ユニーク制約と正規化の考え方を理解する。

## 全体像
ユーザーとメモは1対多。notes.owner_idがusers.idを参照する。

## 🎙 読み上げ可能な講師ナレーション
データベースは保存だけではなく、ルールを持ちます。ユーザーにメモがいくつも紐づく場合、メモ行に所有者IDを置きます。外部キーは存在しないユーザーを参照させない仕組みです。アクセス権限の判定までは自動ではないことに注意しましょう。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```sql
-- owner_idは普通の整数。存在しない利用者も入る
CREATE TABLE notes (id INTEGER, owner_id INTEGER, title TEXT);
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```sql
CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  username TEXT NOT NULL UNIQUE
);
CREATE TABLE notes (
  id INTEGER PRIMARY KEY,
  owner_id INTEGER NOT NULL REFERENCES users(id),
  title TEXT NOT NULL
);
```

## 3. 一行ずつ意味を説明する
1. users.idは利用者レコードを識別する主キー。
2. notes.owner_idがusers.idへ外部キー参照し、孤立したメモを抑える。
3. 外部キーの宣言はアプリケーションのアクセス認可を自動化しない。

## 4. 頭の中で処理の流れを追う
① usersが親テーブル→② notesがowner_idで参照→③ 整合性を検査→④ APIの認可は別に確認。

### 根本原因
DBの関係制約は整合性を守るだけで、アクセス制御を実行するとは限らない。

### 修正の原理
主キーは行の識別、外部キーは参照整合性を守る。ただし外部キーだけで「誰が読めるか」は決まらない。認可は別の仕組み。

### 防御を重ねるとしたら
APIのSELECT/UPDATE/DELETEに認証済みユーザーIDを条件として含める。
