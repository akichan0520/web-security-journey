# 第30章：最終制作：脆弱なコードから堅牢な設計へ

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 総合

## この章でできるようになる
機能要件・認証・認可・入力検証・出力・DB・ログ・テストを一貫して説明する。

## 全体像
自分の「メモ帳＋コメント」サービスを安全な設計で完成させ、他者へ根拠付きで説明する。

## 🎙 読み上げ可能な講師ナレーション
最終課題です。完成させるのは、動くだけの画面ではありません。入力から保存、認可から表示、障害対応までの流れを自分の言葉で説明できるアプリです。初心者の人は正常な機能を完成させ、上級者の人は設計資料、CI、負荷や境界値のテストまで広げてください。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```sql
// 危険：画面で非表示だからサーバーで認可を省く
UPDATE notes SET title = :title WHERE id = :id;
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```sql
// 安全設計例：セッション由来の所有者で絞る
UPDATE notes
SET title = :title
WHERE id = :id AND owner_id = :session_user_id;
-- HTML表示は適切にエンコード
-- 状態変更時はCSRF検証
-- 認証/監査/入力検証もあわせて設計
```

## 3. 一行ずつ意味を説明する
1. UPDATE文に所有者条件がなければ他人のメモ更新を許す設計になる。
2. 認証・認可・CSRF・SQLの値分離・出力エンコードは異なる境界を守る。
3. 「対策が1個あるから安全」ではなく、各機能・各操作で検査する。

## 4. 頭の中で処理の流れを追う
① リクエスト入力→② 検証→③ 認証→④ 所有者の認可→⑤ パラメータ化SQL→⑥ 文脈別の出力→⑦ エラーとログ。

### 根本原因
境界を守る設計そのものが消え、テストが正しくても守るべきものがなくなる。

### 修正の原理
安全性は単一の関数やヘッダーでは完成しない。入力、認証、認可、DB、出力、ログ、テストを一連のデータの旅としてレビューする。

### 防御を重ねるとしたら
機能と脅威を両方レビューし、テスト・設計図・変更履歴を併記する。
