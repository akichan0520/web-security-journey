# 第24章：脅威モデリング・コードレビュー

> **読解教材（実行不要）** — 以下のコードは比較のための断片です。危険版を実行・公開しないでください。

**難易度：** 応用

## この章でできるようになる
資産・攻撃者・入口・信頼境界、データフロー、優先順位付けを説明する。

## 全体像
攻撃手順を思い付く前に、何を守り、誰がどの境界を越えるかを整理する。

## 🎙 読み上げ可能な講師ナレーション
脆弱性一覧を暗記するより、システム図から考える方が応用が利きます。今回はアカウント、メモ、コメント、SQLiteファイルを資産として扱います。ブラウザの入力からPHP、DBまでを矢印で描き、権限検証が必要な場所をマークしましょう。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```text
# 脅威モデルの誤り
「ログイン済み」→「すべてのメモへアクセス可能」と仮定
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```text
資産: 個人メモ
入口: GET /notes?id=123
主体: 認証済みAlice
脅威: 他人のIDへ変更するとBobのメモが返る
境界: URLの値 → サーバーの認可判定
防御: 参照ごとの所有権検証
確認: 他人のIDは取得不可と説明できるか
```

## 3. 一行ずつ意味を説明する
1. 入口（URLパラメータ）は変更可能な未信頼入力。
2. 主体（Alice）と資産（Bobのメモ）の関係が認可の対象。
3. 防御と検証を同じ脅威に対応付ける。

## 4. 頭の中で処理の流れを追う
① 守る資産を決める→② 入口を探す→③ 想定外の主体を考える→④ 対策と確認を対応付ける。

### 根本原因
関数やAPIごとに条件が異なり、不一致から権限抜けが発生する。

### 修正の原理
脅威モデリングでは資産・主体・境界・信頼度を整理する。プログラムの各行ではなく、データが境界を越えるところに注目する。

### 防御を重ねるとしたら
保護すべき資産、入口、脅威、対策、テストを表にしてAPI単位で確認する。
