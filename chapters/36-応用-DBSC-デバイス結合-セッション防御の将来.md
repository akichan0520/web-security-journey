# 第36章：応用：DBSC・デバイス結合・セッション防御の将来

**難易度：** 応用

## この章でできるようになる
従来のBearer CookieとDBSCの違い、仕様と製品展開の違い、現在も残るリスクを説明できる。

## 全体像
DBSCは盗まれたCookie文字列だけで長期利用される問題を抑えるため、ブラウザ側の鍵による更新時の証明を使う。対応条件とリスクは残る。

## 🎙 読み上げ可能な講師ナレーション
最後は2026年の技術動向です。Bearer Cookieは文字列自体を持つことがアクセスの条件になり得ます。DBSCはデバイス結合の鍵を使い、短命なCookieの更新時にその鍵を保有する端末だと証明する仕組みを目指します。W3Cでは標準化作業が進み、Googleは2026年4月にWindows版Chrome 146での一般提供移行とMac版への今後の展開を発表しました。ただし対応ブラウザやサービス次第であり、XSSやマルウェアが使う端末内操作を全て防ぐ保証ではありません。

## 1. 危険なコードを読む
未信頼の値がどこから来て、どの命令や判断へ渡るかに注目してください。

```text
// 設計上の誤解（擬似表現）
Set-Cookie: session=[架空ID]; Secure
// 「Secureがある → コピーしても他の端末で利用不能」ではない
```

## 2. 安全側のコードと比較する
これは設計上の考え方を伝える**抜粋**です。例外処理や周辺設定が省略されている場合があります。

```text
// DBSCの仕組みを抽象化した読解専用モデル
短命なセッションCookieを使用
    ↓ 有効期限に近づく
ブラウザが端末内の秘密鍵で保有証明
    ↓ Webサービス側が検証
対応セッションのCookieを更新
// 注：標準化中であり、ブラウザとサイトの対応が必要
```

## 3. 一行ずつ意味を説明する
1. Bearer Cookieは値そのものが資格情報になることがある。
2. DBSCは端末内で保護された秘密鍵による更新時の保有証明を用いる。
3. Googleの2026年4月公表内容とW3Cのドラフトは、製品展開と仕様という異なる種類の根拠。
4. デバイス結合は端末の完全な健全性を保証するものではない。
5. 既存の期限・失効・XSS対策・認可を置き換えるものではない。

## 4. 頭の中で処理の流れを追う
①短命Cookieを発行→②Cookieの有効期限が近づく→③鍵保有を証明して更新→④サーバーの認可・期限判定→⑤不審時は失効・再認証

### 根本原因
SecureはHTTPS送信を制限するCookie属性であり、デバイス保持鍵による利用者端末の証明ではない。

### 修正の原理
デバイス結合はセッション盗難に対する追加層であり、普遍的なCookie属性でも全サービスに適用済みの機能でもない。

### 防御を重ねるとしたら
失効・検知を土台としたうえで、対応環境に応じてDBSC等のデバイス結合を検討し、利用できる範囲と限界を説明する。
