以下のID・ログ・ドメインはすべて架空。実際のCookieや認証情報を収集するコード、セッションを第三者に送信するコード、攻撃操作は収録しません。

CK-01｜Cookieの正体：パスワードでもプログラムでもない

定義： HTTP Cookieは、Webサーバーが Set-Cookie ヘッダーでブラウザに保存を依頼し、ブラウザが条件を満たす後続要求に Cookie ヘッダーとして添付する名前と値の仕組みです。利用目的はログイン維持、表示設定、買い物かご、分析識別子などさまざま。Cookieが存在すること自体では認証されません。 [C1][C2]

① ブラウザ → サーバー   GET /account
② サーバー → ブラウザ   Set-Cookie: theme=dark; Path=/; SameSite=Lax
③ ブラウザ内部          theme=dark を条件付きで保存
④ ブラウザ → サーバー   Cookie: theme=dark
⑤ サーバー              表示設定として利用（認証とは無関係）

Set-Cookieはレスポンス、Cookieはリクエストです。送られるのは通常値だけで、HttpOnly や Secure などの属性は Cookie リクエストヘッダーに再掲されません。ブラウザが保存時の属性を判断に使用します。[C2]

紙上演習： Cookie: theme=dark が届いたら、この人はログイン済みだと判断できる？

答え判断できません。テーマは表示設定に過ぎません。認証するなら、サーバーが信頼できるセッションや署名・検証済みトークンなどを検証する必要があります。

講師ナレーション： 「Cookieは箱です。中身を誰がどう扱うかによって単なる好みの記録にも、重要なセッション秘密にもなります。」

CK-02｜HTTPは原則ステートレス：どうやってログインを覚えるのか

原理： HTTP要求は原則独立しています。複数回の要求の間で認証状態を保持するため、サーバーがランダムなセッションIDを発行し、保存先にログインユーザーとの対応を記録する設計が広く用いられます。

ブラウザ                      アプリ                     セッション保存先
   │ POST /login（本人確認）     │                            │
   ├───────────────────────────>│ ①認証成功                  │
   │                            ├──② ID と user_id を保存──>│
   │<──③ Set-Cookie: ... ────────┤                            │
   │ GET /account + Cookie      │                            │
   ├───────────────────────────>├──④ IDの期限/失効を確認───>│
   │                            │<──⑤有効なuser_id ──────────┤
   │<──⑥認可した画面────────────┤                            │

Bearer（持参人）型の性質： サーバーが識別子の所持だけでセッションの継続を認める設計では、秘密値が第三者に渡ると有効期間内に不正利用され得ます。ログインに二要素認証を使っても、その後の識別子が保護されるとは限りません。[C5][C6]

紙上演習： ログインパスワードをDBに保存しておけば、Cookieは不要になる？

答え不要にはなりません。毎回パスワードを送る方式には多くの問題があります。認証後のセッション継続を適切に管理します。パスワードは平文保存せず、専用のハッシュ方式で検証します。

講師ナレーション： 「認証は入口、セッションは入館後の継続許可です。守るべき対象は入口だけではありません。」

CK-03｜Cookieヘッダーを1文字ずつ読んでみる

HTTP/1.1 200 OK
Set-Cookie: __Host-session=[架空のランダムID]; Path=/; Secure; HttpOnly; SameSite=Lax
Cache-Control: no-store
部分 役割 間違えやすい点
Set-Cookie: ブラウザに保存を指示するHTTPレスポンスヘッダー HTMLの一部ではない
__Host-session Cookie名。__Host- プレフィックスの制約を利用 対応ブラウザ・正しい属性が必要
[架空のランダムID] サーバーのセッション保存先に関連付く秘密 個人情報やパスワードを直接入れない
Path=/ 対象ホストで送信対象となるパス範囲 アクセス権・秘密の隔離機構ではない
Secure HTTPS等のセキュアな接続でのみ送る属性 端末侵害やXSSによる操作は防げない
HttpOnly JSからのCookie読み取りを制限 ブラウザからの要求にはCookieが付く
SameSite=Lax クロスサイトの送信条件を制御 CSRF対策の一層であって万能ではない
Cache-Control: no-store 機密応答のキャッシュ保存を抑える指示 セッションIDの有効期限管理とは別

__Host- Cookieには Secure、Path=/、Domain属性なしが必要です。Cookieヘッダーにこれらの属性は返ってこないため、サーバーは受信した値だけから元の属性を判断できません。[C2][C3]

紙上演習： Cookie: __Host-session=[架空ID] という要求ヘッダーだけを見て、保存時に HttpOnly があったと断定できる？

答えできません。要求のCookieヘッダーには属性が載らず、ブラウザ側の保存条件やサーバー設定と照合する必要があります。

講師ナレーション： 「HTTPの一行には向きがあります。Set-CookieとCookieを区別できることが、乗っ取り防御の最初の一歩です。」

CK-04｜Expires・Max-Age・セッションCookieと「失効」の違い

Expires は日時、Max-Age は秒数でCookieの保持期間を示します。両方あれば通常 Max-Age が優先されます。どちらもなければ一般にセッションCookieですが、ブラウザの復元機能などによりブラウザを閉じても維持される場合があります。[C2][C3]

最重要の区別： ブラウザからCookieを消すことと、サーバーがセッションIDを受理しなくすることは違います。Cookieを削除しても、第三者が既に持っている同じ値をサーバーが受理すれば不正利用が続き得ます。[C5]

Cookieの保持期間           → ブラウザがいつ捨てるか
セッションのアイドル期限   → 最後の操作からいつ失効させるか
セッションの絶対期限       → 最後のログイン等から最長いつまでか
サーバー側の明示失効       → IDを以後受け付けない操作

紙上演習： ログアウト時に Max-Age=0 を送るだけで、窃取済みのセッションIDも安全になる？

答え安全とは限りません。ブラウザ側削除と並行して、サーバー側でセッションを失効させる必要があります。期限判定もサーバー側で強制します。

講師ナレーション： 「ブラウザが忘れることと、サーバーが拒否することは別です。侵害時に本当に必要なのはサーバー側の拒否です。」

CK-05｜Domain・Path・Secure・HttpOnlyを混同しない

  • Domainなし：原則そのホストに限定する host-only Cookie。共有範囲が狭く、認証用途で推奨されやすい。
  • Domainあり：指定ドメインと対象サブドメインに広がる。サブドメインの信頼を慎重に評価。
  • Path：送信するパスのフィルタ。セキュリティ境界ではない。同一ホスト内のパス同士を隔離する目的には不適切。
  • Secure：通常のHTTP平文通信での送信を制限。ただし、端末侵害や正規接続中の悪用を防ぐものではない。
  • HttpOnly：document.cookie 等からの読み取りを制限。一方、fetch() 等の通信条件に応じてCookie自体は自動送信され得る。[C2][C3]

反例（概念比較）

Set-Cookie: session=[架空ID]; Domain=example.test; Path=/; Max-Age=2592000

この反例は「絶対に漏れる」という意味ではありません。ただし Secure、HttpOnly、SameSite がなく、共有範囲が広く、長期有効で、リスクを増やし得る設定です。

紙上演習： Path=/admin にすれば同一ドメインの別のアプリからCookieを守れる？

答えいいえ。Pathは送信範囲のヒントであり、安全なアプリ分離の境界ではありません。異なる信頼領域は別ホストなどに分離します。

講師ナレーション： 「Cookie属性は『誰に何を制限するか』をそれぞれ区別して理解しましょう。」

CK-06｜SameSiteを理解する鍵は「サイト」と「オリジン」

オリジン（origin） は原則 スキーム + ホスト + ポート の組。サイト（site） は原則スキームと登録可能ドメインで判断する考え方です。サブドメインやポートの違いで同じサイトだが異なるオリジンとなることがあります。CORSのsame-originとCookieのSameSiteを同一視してはいけません。[C3][C7]

SameSite 主な挙動 トレードオフ
Strict クロスサイト要求では基本的に送らない 外部サイトからのリンク遷移でログイン状態が扱いにくい場面
Lax クロスサイトでのトップレベル安全メソッド遷移などには送られ得る 通常のUXとCSRF軽減のバランス
None クロスサイトにも送信可能（Secureが必要） 埋め込み利用など。別途CSRF・プライバシー対策が重要

注意： 省略時の既定挙動や例外はブラウザ・バージョンに依存し得ます。SameSiteを指定しただけでCSRFが絶対に防げるとは断定しないでください。重要な状態変更にはサーバー側のCSRF対策も組み合わせます。[C3][C8]

紙上演習： portal.example.test と api.example.test はsame-origin？ same-site？

答えホストが違うためsame-originではありません。同じスキームで同じ登録可能ドメインなら一般にsame-siteです（`example.test` は説明用名）。この違いがCookie・CORS・CSRFの設計を複雑にします。

講師ナレーション： 「originとsiteは似ていて別のルールです。SameSiteはCORSを置き換える機能ではありません。」

CK-07｜__Host-、__Secure-、Partitioned、CHIPSを読む

Cookieプレフィックスは対応ブラウザがセット時に属性制約を検証するための命名規則です。

接頭辞 ブラウザ側で求められる主な制約
__Secure- Secureな接続と Secure 属性
__Host- 上記に加え、Domain なし、Path=/
__Http- Secureな接続、Secure、HttpOnly。対応状況に注意
__Host-Http- __Host- と __Http- の制約の組合せ。対応状況に注意

CHIPS（Partitioned Cookie）は、第三者のCookieをトップレベルサイトごとの区画で保持する仕組み。Cookie盗難そのものを防ぐ暗号技術ではありません。埋め込み用途や追跡防止などに関わるブラウザの保存・送信範囲の機能です。[C3][C10]

Set-Cookie: __Host-widget=[架空値]; Secure; Path=/; SameSite=None; Partitioned

紙上演習： Set-Cookie: __Host-session=...; Domain=example.test; Path=/; Secure は期待通り保存される？

答え対応ブラウザでは `__Host-` の条件に反する `Domain` 属性があるため拒否されます。プレフィックスの文字列を付けるだけでなく、制約に従う必要があります。

講師ナレーション： 「Cookieの名前には、設定を強制する仕組みがあります。ただし利用するブラウザの対応状況まで確認が必要です。」

CK-08｜JavaScript・localStorage・sessionStorageと認証情報

保存先 JSから読み出し 自動送信 主なリスク・注意
HttpOnly Cookie 通常不可 Cookie条件による XSSでCookieを読めなくても不正要求は成立し得る
JSから読めるCookie 可 Cookie条件による XSSで内容を読まれ得る
localStorage 可 自動では送信されない XSSで値が読まれ得る。長期保存になる場合
sessionStorage 可 自動では送信されない タブ単位の寿命が主。XSSの影響を受け得る

よくある誤解： 「localStorageならCookieの乗っ取りはゼロ」。ブラウザが勝手に添付しない代わりに、JavaScriptからアクセスできるため、XSS時の資格情報窃取リスクを考えます。HttpOnly Cookieを使ってもCSRF等の対策が不要になるわけではありません。[C3][C5]

紙上演習： HttpOnly設定をしていれば、XSSはログイン中の重要操作を行えない？

答えそうとは限りません。XSSが同じWebアプリの実行コンテキストで動くと、ブラウザがCookieを伴う要求を送る場合があります。文脈別出力エスケープやCSP、重要操作への再認証などが必要です。

講師ナレーション： 「読み取られる危険と、利用者のブラウザに操作をさせる危険は分けて考えます。」

CK-09｜PHPのセッションはどこに保存される？

PHPでは session_start() によってセッションを開き、$_SESSION に状態を保存するのが基本です。ただし、実際の保存先はハンドラや設定によってファイル、Redis、DBなどがあり得ます。

<?php
// 概念説明：リクエスト開始前にセッション設定済みとする
session_start();
$_SESSION['user_id'] = 42;
// Cookieには通常 user_id=42 そのものではなくセッションIDが載る

流れ： Cookie: PHPSESSID=...（名称は設定による）→PHPが識別子を確認→保存先にアクセス→ $_SESSION['user_id'] を利用する。認可はここからさらに必要です。

session.use_strict_mode=1 は未初期化の外部由来IDを拒否する設定で、セッション固定の緩和に重要です。ただし、既に有効なIDの窃取に対する万能策ではありません。[C9]

紙上演習： $_SESSION['user_id'] があれば、注文IDさえ指定できれば他人の注文を読んでもよい？

答えよくありません。ログインの確認と個々の注文の所有者・権限確認は別です。認証だけではIDOR/BOLAを防げません。

講師ナレーション： 「セッションにユーザーIDが保存されていても、データの操作権限までは自動では決まりません。」

CK-10｜PHPの安全側コードを行ごとに解剖する

以下はセッション初期設定部分の読解用です。完全な認証実装ではなく、HTTPSを前提とします。

<?php
declare(strict_types=1);
ini_set('session.use_strict_mode', '1');
ini_set('session.use_only_cookies', '1');
session_name('__Host-session');
session_set_cookie_params([
    'lifetime' => 0,
    'path' => '/',
    'secure' => true,
    'httponly' => true,
    'samesite' => 'Lax',
]);
session_start();
行 役割 限界・補足
strict_types PHPの型の扱いを厳格化する宣言 セッション安全性の直接対策ではない
session.use_strict_mode 未初期化IDを拒否 有効な盗難IDまで必ず拒否するわけではない
session.use_only_cookies URLなどによるID受け渡しを避ける Cookie漏えいまでは防げない
session_name('__Host-session') 安全なスコープ制約を使いやすくする 属性が条件に合っている必要がある
lifetime=0 Cookieに永続期間を付けない サーバー期限の代わりにはならない
path='/' __Host-の必須条件 Pathは認可境界ではない
secure=true HTTPSでのみ送信 HTTPSサイト前提。HTTPでは通常送られない
httponly=true JSによるCookie参照を抑える CSRFやXSS由来の操作は別対策
samesite='Lax' クロスサイト時の送信制限 重要操作はCSRF対策も必要
session_start() 保存先のセッションを開く 設定は前に行う必要がある

注意： ini_set の設定可否やカスタムセッションハンドラの挙動は環境で確認が必要です。サーバー側の期限・セッションストア・失効・ログアウト処理、セッションID再生成、例外処理は別途設計します。[C9][C11]

紙上演習： session_start() の後で session_set_cookie_params() すれば現在のCookieに必ず反映される？

答えいいえ。PHP公式は `session_start()` 前に設定するよう案内しています。先に開始してしまうと期待通り反映されません。

講師ナレーション： 「安全な設定も、適用する順番を間違えると効果がありません。コードは1行ずつ読みます。」

CK-11｜セッション固定：盗まなくても起こり得る脅威

セッション固定（Session Fixation）は、攻撃者が事前に把握するセッションIDを認証後も使わせる問題です。単純なセッション窃取（ログイン後に盗むこと）とは異なります。成否は、IDの導入経路、サーバーの厳格モード、認証前後のID再生成、古いIDの扱いなどに依存します。[C5][C9]

認証前ID: 旧ID（認証されていない状態）
             │ ログイン成功
             ▼
認証後ID: 新ID（独立したランダム識別子）
             │ 旧IDは認証済み権限を持たせない
             ▼
サーバー側で期限・失効・所有者を照合

改善の柱： 認証時/権限変更時のセッションID再生成、古いIDの安全な扱い、Strict Mode、有効期限、サーバー側失効。session_regenerate_id() の利用では競合要求やモバイル通信の切断、古いセッションの破棄時点も含めて公式マニュアルの注意事項を読む必要があります。[C9][C12]

紙上演習： ログイン前に同じIDが保存され、ログイン後もIDが変わらない設計はなぜ問題？

答え認証前にIDを知っていた主体が、そのIDを認証後にも利用できる設計になり得るためです。認証の境界で新しいIDに切り替える必要があります。

講師ナレーション： 「盗まれたIDと、先に知られていたID。どちらも『本人以外が識別子を持つ』ことが共通の危険です。」

CK-12｜Cookie窃取とセッションハイジャックの分類

脅威モデリングでは、被害が発生したという結果と、そこに至った原因を切り分けます。

経路 攻撃者が得るもの／起こすこと 防御の中心
情報窃取型マルウェア 端末やブラウザ内のセッション情報 端末保護、セッション失効、セッション結合技術
悪意あるブラウザ拡張 権限の過剰な拡張機能を通じた閲覧・操作 拡張の制限・監査、機密情報の保護
XSS ブラウザ内の任意動作、設定によっては値の読取 出力文脈別エスケープ、危険なAPI回避、CSP
通信やログの漏えい セッション秘密が外部へ露出 TLS、秘密をURL/ログに含めない
セッション固定 認証前に知られているIDを認証後に利用 認証時ID更新、厳格モード
CSRF Cookieの自動送信を悪用した本人ブラウザでの操作 CSRFトークン、Origin検証、SameSite

CSRF ≠ Cookie窃取、XSS ≠ Cookie窃取。XSSでCookieを読めない設計でも、同じオリジン上の操作権限を悪用できる場合があります。経路と目的を分けると防御の理由が明瞭になります。[C5][C6][C8]

紙上演習： HttpOnly なのにログイン中に勝手に設定が変わった。どんなリスクが残る？

答え同一サイトでのXSSによる操作、CSRF、アプリの認可不備、侵害端末からの正規に見える要求などが考えられます。HttpOnlyの役割はCookieのJS読み取り制限であり、それ以外を完全防御するものではありません。

講師ナレーション： 「同じ被害に見えても、原因によって必要な対策は違います。用語を混ぜないことが調査の第一歩です。」

CK-13｜MFA・パスキーがあってもセッションが危険な理由

MFA・パスキーは主にログイン過程での本人確認を強化します。しかしログイン済みのセッション識別子をサーバーが持参人型で扱う場合、識別子自体の盗難が有効期間内の不正利用を可能にし得ます。強い認証を否定する話ではなく、認証後の秘密を別の層で守るという話です。[C5][C6]

認証前：パスワード / パスキー / MFA → 本人確認に成功
認証後：セッションID → 多数の要求のたびに継続判定
         ↑ このIDが失われれば認証の強さとは別の問題が生じる

設計判断： 重要操作（送金・秘密変更・管理者操作）には、通常のセッション継続に加え、再認証・独立した確認・明示的な権限の再評価を検討します。ただし再認証要求は全ての攻撃を防ぐわけではありません。

紙上演習： パスキー必須としたら、セッション失効機構を削除してよい？

答えいいえ。セッション秘密が侵害された場合の遮断、端末紛失、ログアウト、期限、権限変更に対応するため、失効機構は必要です。

講師ナレーション： 「強い入口と、強い滞在管理はセットで必要です。片方だけでは十分ではありません。」

CK-14｜セッション保存先・失効・ローテーション・同時ログイン

有効なセッションをサーバー側で識別・失効できる設計では、保存データの例として session_id_hash / user_id / created_at / last_seen_at / absolute_expires_at / revoked_at / device_label などを検討できます。生のセッションIDはデータベースやログにも不要に残さないことが望まれます。照合用にはセッション秘密の適切なハッシュ化等を検討します。

要求が来たら
  ① Cookieを取得（なければ未認証）
  ② 保存先を照合（存在しなければ拒否）
  ③ revoked_at / idle期限 / 絶対期限を検証
  ④ 必要なら権限変更・端末リスクを評価
  ⑤ 対象APIの認可を検証して応答

同時ログイン：端末ごとにセッションを分ける設計なら、「この端末だけログアウト」と「全端末でログアウト」を区別できます。パスワード変更・重大な権限変更時はどのセッションを無効化するかを定義します。

ローテーション：頻繁な再発行だけでなく、古いIDがいつ無効になるか、通信競合時の扱い、端末側の状態管理が重要です。[C5][C6]

紙上演習： アカウントのパスワードを変えた直後、既存セッションは必ず自動的に失効する？

答え自動とは限りません。アプリの設計次第です。パスワード変更時の一括失効や重要セッションの再認証を明示して実装する必要があります。

講師ナレーション： 「アカウントとログイン端末を区別すると、どの権限を取り消すべきかが明確になります。」

CK-15｜CSRFはなぜ起きる？ Cookieが「自動」で送られるため

ブラウザは条件に一致するCookieを自動で添付します。これが便利な一方、悪意ある別サイトから利用者のブラウザに状態変更要求を送らせる脅威（CSRF）の背景になります。Cookieを盗む必要はありません。 [C8]

多層防御： サーバー側CSRFトークン、Origin 等の検証、状態変更に適切なHTTPメソッド、必要に応じてSameSite、重要操作の再認証など。GET が状態を変更する設計は避け、SameSite のみを唯一の対策としないでください。

<?php
// 設計上の対比（呼び出し先・フォーム全体は省略）
// NG: 状態変更を $_GET['action'] だけで認める
// OK: 認証済み＋認可済み＋CSRFトークン照合＋適切なメソッドを要求

紙上演習： HttpOnly があるのにCSRF対策が必要なのはなぜ？

答えHttpOnlyはJSからCookieを読ませない属性で、ブラウザが要求にCookieを添付する動作は変えません。操作が正当な意図によるものかは別途確認します。

講師ナレーション： 「Cookieを見せなくてもCookieが勝手に付く。この二つは両立します。そこがCSRFを理解するポイントです。」

CK-16｜JWT、OAuth、アクセストークンとCookieの違い

JWTはデータ形式、Cookieは送信・保存の仕組みです。JWTをCookieに入れることも、Authorization: Bearer ... で送ることもできます。JWTの署名は改ざん検出に役立ちますが、署名が有効でも盗まれた持参人トークンが有効期間内に利用され得るという問題は変わりません。

  • JWTの署名検証：署名鍵・許可アルゴリズム・iss（発行者）・aud（受信者）・exp（期限）などを正しく検証。
  • 失効の難しさ：完全な自己完結型トークンは失効処理に工夫が必要。短寿命、サーバー側拒否リスト、セッション連動、リフレッシュトークン管理を検討。
  • OAuth：他サービス等への限定的なアクセスを認可する枠組み。OAuth自体はCookieでもログインそのものでもない。
  • OIDC：OAuth上に認証情報の層を提供する仕様。Cookie管理とは役割を分ける。

紙上演習： JWTを署名したのでパスワードが漏れず安全、という主張の誤りは？

答え通常の署名付きJWTのペイロードは暗号化されず読めます。署名は主に改ざん検出・発行者等の検証であり、Bearerトークンの盗難・再利用を防ぐものではありません。

講師ナレーション： 「名前ではなく役割で整理しましょう。Cookieは運び方、JWTは形式、OAuthは委任、セッションは状態管理です。」

CK-17｜ログから盗難セッションの兆候を読む：SOC/CSIRT編

絶対に認証トークンの生値をログに書かないことを前提に、セッション単位を示す安全な識別子（ハッシュや別の監査ID）を扱います。IP/UAは変化し得るため、変わっただけで侵害確定ではありません。[C6]

2026-10-20 10:00  sid_tag=A7  login_ok      ip_group=JP-1  ua_family=Mobile  risk=low
2026-10-20 10:02  sid_tag=A7  view_profile  ip_group=JP-1  ua_family=Mobile  risk=low
2026-10-20 10:04  sid_tag=A7  export_data   ip_group=Unknown-2 ua_family=Desktop risk=high
2026-10-20 10:05  sid_tag=A7  revoke        reason=manual_review

読み方： 最初の2件は同一セッションの通常操作、3件目はセッション識別子が同じまま通信特性と行為が変わったため追加調査の候補。VPN、携帯網、社内プロキシ、OS更新等でIP/UAの変化は生じ得ます。確定診断には複数の文脈情報が必要です。

推奨する観点： 異常な地域/ASN変化、同時期の互いに不自然な利用、通常と異なる操作、権限変更、失敗認証との関連、端末管理状況、脅威インテリジェンスとの照合。監視には保存期間・アクセス制御・個人情報保護も必要です。[C6]

紙上演習： sid_tag=A7 のIPが変化した。アラートを即時に「侵害確定」にすべき？

答え確定とはしません。高リスクな操作などと組み合わせて評価し、必要ならステップアップ認証・当該セッションの一時失効を判断します。誤検知と検知漏れの両方を考慮します。

講師ナレーション： 「ログ分析で重要なのは単一の怪しい値より、同じセッションの時間的な変化と操作の文脈です。」

CK-18｜侵害時に何をする？ 失効・端末調査・再認証

ケース： 利用者から「身に覚えのないアカウント操作」の報告を受けた。セッション乗っ取りの疑いはあるが、原因は未確定。

  1. 影響範囲を把握：対象アカウント、現在のセッション、実行された重要操作、ログの保全。
  2. 被害の継続を止める：疑わしいセッションや必要な全セッションをサーバー側で失効。重要操作を一時制限する判断も。
  3. 端末・拡張・認証要素を確認：マルウェアや不審拡張機能の可能性。パスワードを変更するだけで十分とは限らない。
  4. 認証と状態を回復：安全な端末から再認証、必要に応じてパスキーやMFAの再確認、連携サービス・APIトークンの失効。
  5. 記録と改善：原因別の再発防止、監視条件、設計変更、利用者連絡。法令/規程に沿った報告判断。

重要： ブラウザのCookie削除のみでは第三者が持つコピーを無効化できません。また、感染端末を放置すれば再ログインしても再侵害され得ます。[C5][C6]

紙上演習： 端末感染が疑われるのに、同じ端末ですぐパスワード変更して終了する方法の問題点は？

答え感染要因が残っていれば新しい資格情報や新セッションが再び露出する可能性があります。セッション失効、端末調査・隔離、安全な端末での再認証などを連動させます。

講師ナレーション： 「漏れた情報の再利用を止め、さらに同じ原因で漏れない状態に戻す。二段階の対応が必要です。」

CK-19｜DBSC・デバイス結合と将来の防御：何が変わる？

従来のBearerセッションでは、秘密値の所持だけで継続できる設計が主流です。Device Bound Session Credentials（DBSC） は、端末側に保持する鍵に基づく署名等で端末が鍵を保持することの証明を求め、Cookieだけを別端末へ持ち出す攻撃の価値を下げる発想です。実装・ブラウザ対応・サービス側の採用状況は変化します。技術仕様の存在と、全サービスへの適用を混同しないでください。[C7][C13]

従来：ブラウザ ─[セッションID]─> サーバー
                漏れたIDがそのまま使える場合がある

端末結合型の発想：ブラウザ ─[更新要求＋端末鍵の証明]─> サーバー
                          ただのIDコピーだけでは継続しにくい

残るリスク： 同じ端末上での侵害・セッション内の不正操作、ブラウザの実装や結合の対象外、復旧・端末移行・鍵喪失、旧方式との併用など。DBSCを導入したらXSSやCSRFが解決するわけではありません。

紙上演習： 「DBSC対応ブラウザがある」＝「すべてのWebサービスのCookie乗っ取りが防げる」？

答えいいえ。サーバー側の採用・接続条件、端末での鍵の保護、適用範囲によって効力が決まります。現行のセッション失効やXSS対策なども必要です。

講師ナレーション： 「未来の対策は盗まれた秘密の価値を下げますが、すべての攻撃が消えるわけではありません。」

CK-20｜総合ケーススタディ：設計レビューを完成させよう

架空サービスの設定： ログインはパスキー対応。Set-Cookie: SID=[架空ID]; Domain=example.test; Max-Age=2592000 で管理。サーバーはログアウト時にCookie削除だけ行う。ログに Cookie: の値を記録。管理画面の設定変更にCSRF検証なし。すべての端末で同じセッションIDを使い、重要操作に追加認証を求めない。

レビュー課題： 不備を6個以上見つけ、①原因、②悪用の成立条件、③優先対策、④対策しても残るリスクを説明する。

模範解答（理由つき）
  1. Cookieの属性不足：Secure / HttpOnly / SameSite / 必要に応じて __Host- などを検討。属性で端末感染は防げない。
  2. Domainが広い：サブドメインが混在するならhost-only設計が望ましい。ホスト侵害自体は別の問題。
  3. 長期間の識別子利用：アイドル/絶対期限をサーバー側で強制し、高リスク操作は再認証。期限内の盗用は残る。
  4. ログアウトの処理：Cookieを消すだけでなく、サーバー側保存先でIDを失効させる。失効前の操作は既に発生した可能性がある。
  5. ログに秘密を書いている：生Cookieを記録せず別の監査識別子を使い、過去ログの保護・削除範囲を調査。
  6. CSRF検証不足：重要な状態変更はCSRFトークンやOrigin検証を導入。SameSiteだけでは万能ではない。
  7. 全端末同じID：端末ごとにセッションを分離して影響範囲を局所化。アカウント全体の侵害には一括失効も必要。
  8. 重要操作の追加確認なし：高リスク操作を再認証・ステップアップで保護。ただし同一端末侵害には追加考慮が必要。
  9. 端末侵害の検知/対応不足：ログ・リスクベース判断・セッション管理画面・失効導線を設計。IP変化だけで侵害を断定しない。

講師ナレーション： 「『属性を足せば全部安全』ではありません。認証・セッション・アプリ・端末・監視の5層に分けて考えると、脆弱性を見逃しにくくなります。」

  2. 盗まれた有効セッションがMFAを迂回するように見えるのはなぜ？ 防御を3層に分けると？
